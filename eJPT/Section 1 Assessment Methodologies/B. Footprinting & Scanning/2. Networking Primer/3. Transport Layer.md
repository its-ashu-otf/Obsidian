### 🔁 Transport Layer – OSI Model (Layer 4)

The **Transport Layer** is the **fourth layer** of the OSI model and plays a **critical role in ensuring complete data delivery** between two devices communicating across a network.

---

#### 📌 **Core Responsibilities:**

1. **End-to-End Communication:**
    
    - Provides **logical communication** between applications on different hosts.
        
    - Ensures that the **sender and receiver are correctly connected**.
        
2. **Segmentation and Reassembly:**
    
    - Breaks large messages/data streams into **smaller segments** at the sender’s side.
        
    - Reassembles the segments back into the original message at the receiver’s side.
        
3. **Error Detection & Correction:**
    
    - Verifies that the transmitted data is **not corrupted**.
        
    - If errors are detected (in TCP), **retransmission** is requested.
        
4. **Flow Control:**
    
    - Manages the **rate of data transmission** between devices.
        
    - Prevents a **fast sender** from overwhelming a **slow receiver**.
        
5. **Reliable vs. Unreliable Transmission:**
    
    - Ensures **reliable** and **ordered** delivery in **TCP**.
        
    - Allows **faster**, connectionless communication in **UDP**, which doesn’t guarantee delivery.
        

---

#### 🔀 **Key Protocols at the Transport Layer:**

|**Protocol**|**Type**|**Features**|
|---|---|---|
|**TCP (Transmission Control Protocol)**|Connection-oriented|Reliable, ordered, error-checked data delivery; supports acknowledgments and retransmissions.|
|**UDP (User Datagram Protocol)**|Connectionless|Fast, low-latency transmission; no guarantee of delivery, order, or error correction. Useful for real-time apps like VoIP or streaming.|

---

### 🔀 Transport Layer Protocols (OSI Layer 4)

The **Transport Layer** provides communication services directly to the **application layer** and ensures the proper transmission of data between hosts. Two main protocols operate here:

![[Pasted image 20250420220838.png]]

---

#### 1. 📦 **TCP (Transmission Control Protocol)**

- **Type:** Connection-oriented
    
- **Key Features:**
    
    - Establishes a **reliable connection** using a **3-way handshake**.
        
    - Guarantees **ordered delivery** of data.
        
    - Performs **error checking**, **acknowledgments**, and **retransmission** of lost packets.
        
    - Implements **flow control** and **congestion control**.
        
- **Use Cases:**
    
    - Web browsing (HTTP/HTTPS)
        
    - File transfers (FTP)
        
    - Email (SMTP, IMAP, POP3)
        
- **Example Ports:**
    
    - HTTP (80), HTTPS (443), FTP (20/21), SSH (22)
        

---

#### 2. ⚡ **UDP (User Datagram Protocol)**

- **Type:** Connectionless
    
- **Key Features:**
    
    - Sends data without establishing a connection — **no handshakes**.
        
    - **Faster** and more efficient due to minimal overhead.
        
    - No guarantees of **delivery**, **order**, or **error correction**.
        
    - Ideal for time-sensitive applications.
        
- **Use Cases:**
    
    - Video/audio streaming
        
    - Online gaming
        
    - DNS lookups
        
    - VoIP (Voice over IP)
        
- **Example Ports:**
    
    - DNS (53), DHCP (67/68), SNMP (161)
        

---

### 📦 TCP – Transmission Control Protocol (OSI Layer 4)

**TCP (Transmission Control Protocol)** is one of the most essential protocols at the **Transport Layer (Layer 4)** of the OSI model. It ensures **reliable**, **ordered**, and **error-checked delivery** of data between two systems in a network.

---

#### 🔌 **Key Features of TCP**

---

#### ✅ **1. Connection-Oriented Communication**

- TCP is a **connection-oriented protocol**, meaning it **establishes a connection** before data transfer begins.
    
- This is achieved using the **TCP 3-way handshake**:
    
    1. SYN (synchronize)
        
    2. SYN-ACK (synchronize-acknowledge)
        
    3. ACK (acknowledge)
        

This process creates a **virtual circuit** between the sender and receiver, ensuring both ends are ready for communication.

---

#### 🔁 **2. Reliability**

- TCP guarantees **data delivery**.
    
- Uses **acknowledgments (ACKs)** to confirm successful receipt of data.
    
- If a segment is lost or corrupted, **TCP will retransmit** it.
    
- Ensures **no data loss** occurs during transmission.
    

---

#### 🔀 **3. Ordered Data Transfer**

- TCP assigns **sequence numbers** to each segment.
    
- If packets arrive **out of order**, TCP reorders them before handing the data to the application layer.
    
- Maintains **data integrity and order** across the session.
    

---

#### 🧠 Additional TCP Mechanisms:

- **Flow Control:** Uses **window size** and **sliding window** technique to avoid overwhelming the receiver.
    
- **Congestion Control:** Adjusts the rate of data transmission based on network congestion (using algorithms like slow start, congestion avoidance).
    
- **Error Detection:** Incorporates **checksums** in the TCP header to detect data corruption.
    

---

#### 🤝 TCP 3-Way Handshake (Connection Establishment)

The **TCP 3-Way Handshake** is a **three-step process** used to **establish a reliable connection** between a client and server **before** data transmission begins. It ensures that both parties are synchronized and ready to communicate.

---

### 🔄 **Steps in the 3-Way Handshake:**

#### 1. **SYN (Synchronize) – Step 1:**

- **Client → Server**
    
- The client initiates the connection by sending a **SYN** (Synchronize) flag set.
    
- This packet includes the client’s **initial sequence number (ISN)** which is a randomly chosen value.
    

📝 Purpose: "Hey, I want to start a connection and here’s my starting sequence number."

---

#### 2. **SYN-ACK (Synchronize-Acknowledge) – Step 2:**

- **Server → Client**
    
- The server responds with a **SYN-ACK** packet:
    
    - **SYN**: To acknowledge the connection and send its own sequence number.
        
    - **ACK**: Acknowledges the client’s sequence number (ISN + 1).
        

📝 Purpose: "I acknowledge your request and here’s my own sequence number."

---

#### 3. **ACK (Acknowledge) – Step 3:**

- **Client → Server**
    
- The client sends a final **ACK** packet to confirm receipt of the server’s SYN.
    
- It includes the server’s ISN + 1 in the acknowledgment number.
    

📝 Purpose: "I received your response. Let’s start sending data."

---

#### ✅ **Connection Established!**

Once the 3-way handshake completes, a **full-duplex TCP connection** is established, and **data transmission can begin**.

- After the three-way handshake is complete, the devices can exchange data in both directions.

- The acknowledgment numbers in subsequent segments are used to confirm the receipt of data and to manage the flow of information.

### TCP Header Fields

![[Pasted image 20250420223859.png]]

 This diagram shows the **TCP header format**, which is part of the TCP segment structure used at the **Transport Layer (Layer 4)** of the OSI model. Let's break it down field by field:

---

#### 🔍 **TCP Header Fields (20 bytes minimum, up to 60 bytes)**

|Octet Range|Field|Description|
|---|---|---|
|**0 - 1**|**Source Port**|The port number of the **sender** (e.g., 443 for HTTPS, 80 for HTTP).|
|**2 - 3**|**Destination Port**|The port number of the **receiver**.|
|**4 - 7**|**Sequence Number**|The starting sequence number of the first byte of data in this segment. Used for ordered delivery and reassembly.|
|**8 - 11**|**Acknowledgment Number**|If ACK flag is set, this field holds the **next expected byte** from the sender.|
|**12 (bits 0–3)**|**Data Offset**|Tells how long the TCP header is (in 32-bit words). Important for finding where data begins.|
|**12 (bits 4–7)**|**Reserved**|Reserved bits for future use, usually set to 0.|
|**13 (Control Flags)**|**Flags (9 bits)**|Controls connection setup/teardown and data flow. Detailed below ↓|
|**14 - 15**|**Window Size**|Specifies how much data the sender can accept (flow control).|
|**16 - 17**|**Checksum**|Error-checking for the header and data.|
|**18 - 19**|**Urgent Pointer**|Used if the URG flag is set; points to urgent data.|
|**20+**|**Options (Optional)**|Varies in size. Used for things like MSS, timestamps, and window scaling.|
|**...**|**Padding**|Added to ensure header ends on a 32-bit boundary (multiple of 4 bytes).|

---

#### 🚩 **Control Flags (Bit-level)**

Each flag is **1 bit**, meaning it can be either 0 (off) or 1 (on). Here's what each one does:

|Bit|Flag|Description|
|---|---|---|
|**C**|**CWR (Congestion Window Reduced)**|Used in congestion control.|
|**E**|**ECE (ECN Echo)**|Congestion notification support.|
|**U**|**URG (Urgent)**|Data should be processed immediately.|
|**A**|**ACK (Acknowledgment)**|Acknowledgment field is valid.|
|**P**|**PSH (Push Function)**|Asks to push data to receiving application immediately.|
|**R**|**RST (Reset)**|Resets a connection (aborts it).|
|**S**|**SYN (Synchronize)**|Used to initiate a connection (1st step of 3-way handshake).|
|**F**|**FIN (Finish)**|Gracefully terminate a connection.|

---

#### 🧠 **Helpful Notes:**

- The **minimum size of a TCP header is 20 bytes**, if there are no options.
    
- **Options** make the header longer and are used for features like **Window Scaling**, **MSS (Maximum Segment Size)**, and **Timestamps**.
    
- **Data Offset** helps the receiver know where the **header ends and the actual data starts**.
    

---

#### 🔐 TCP Control Flags (6 Key Flags Out of 9 Total)

|Flag|Full Name|Function|
|---|---|---|
|**SYN**|Synchronize|Used to initiate a connection.|
|**ACK**|Acknowledgment|Acknowledges received data or connection request.|
|**FIN**|Finish|Gracefully ends a connection.|
|**RST**|Reset|Immediately aborts a connection.|
|**PSH**|Push|Push data to the application immediately.|
|**URG**|Urgent|Indicates urgent data is present.|

---

#### 📡 **TCP Connection Establishment: 3-Way Handshake**

| Step       | Sender Flags | Receiver Flags | Description                                                        |
| ---------- | ------------ | -------------- | ------------------------------------------------------------------ |
| 1. SYN     | SYN=1        | —              | Client initiates connection with sequence number (e.g., `SEQ=100`) |
| 2. SYN-ACK | SYN=1, ACK=1 | SYN=1, ACK=1   | Server responds with its own `SEQ` and acknowledges the client's.  |
| 3. ACK     | ACK=1        | —              | Client sends acknowledgment, connection is established.            |

---

#### 🔚 **TCP Connection Termination (4-Step Process)**

|Step|Who|Flags|Description|
|---|---|---|---|
|1. FIN|Client|FIN=1|Client initiates connection termination.|
|2. ACK|Server|ACK=1|Server acknowledges termination request.|
|3. FIN|Server|FIN=1|Server also initiates termination.|
|4. ACK|Client|ACK=1|Client acknowledges, connection is closed.|

---

#### 🧪 **Flag Status Examples**

#### ✔ **Connection Establishment:**

- `SYN = 1`: Start handshake
    
- `ACK = 0`: No acknowledgment yet (first step)
    
- Then `SYN = 1`, `ACK = 1`: Response from the server
    
- Final `ACK = 1`: Client confirms
    

#### ✔ **Connection Termination:**

- `FIN = 1`: Initiates termination
    
- `ACK = 1`: Acknowledges termination
    
- Eventually both `FIN = 1` and `ACK = 1` exchanged.

## 🔢 TCP Port Ranges (0–65535)

TCP port numbers are **16-bit unsigned integers**, so the range is:

```
0 to 65535
```

These are divided into **three main categories**:

---

### 1️⃣ **Well-Known Ports (0–1023)**

- **Reserved by IANA**
    
- Used by **core protocols and services**
    
- **Require root/admin privileges** to bind on Unix/Linux systems
    

|Port|Service|
|---|---|
|20/21|FTP (File Transfer Protocol)|
|22|SSH (Secure Shell)|
|25|SMTP (Simple Mail Transfer Protocol)|
|53|DNS (Domain Name System)|
|80|HTTP (Web traffic)|
|110|POP3 (Email receiving)|
|443|HTTPS (Secure web traffic)|

---

### 2️⃣ **Registered Ports (1024–49151)**

- **Assigned by IANA** to vendors and applications
    
- Not reserved, but commonly used
    
- **Non-privileged** applications can bind to these
    

|Port|Service|
|---|---|
|1433|Microsoft SQL Server|
|3306|MySQL Database|
|3389|Remote Desktop Protocol (RDP)|
|5432|PostgreSQL|
|27017|MongoDB|
|8080|HTTP alternate port (often used for proxies or test servers)|

---

### 3️⃣ **Dynamic or Private Ports (49152–65535)**

- **Not assigned by IANA**
    
- Used for **ephemeral (temporary) ports**
    
- Often automatically selected by client devices when initiating connections
    

|Use Case|
|---|
|Browser connecting to a web server|
|SSH client making outbound connection|
|Applications using NAT/firewall|

---

## UDP – User Datagram Protocol (Transport Layer | Layer 4)

![[Pasted image 20250420224423.png]]

UDP is a **connectionless**, **lightweight**, and **stateless** protocol used to send data with **low latency** and **minimal overhead**.

---

### 🔑 **Key Characteristics**

| Feature                 | Description                                                                                     |
| ----------------------- | ----------------------------------------------------------------------------------------------- |
| **Connectionless**      | No connection setup/tear-down before sending data.                                              |
| **Unreliable**          | No acknowledgment, retransmission, or ordering. Lost or out-of-order packets are not corrected. |
| **Stateless**           | Each datagram is sent independently. No session info is tracked.                                |
| **Low Overhead**        | Fewer headers (8 bytes only), making it fast and efficient.                                     |
| **Speed > Reliability** | Prioritizes fast transmission over guaranteed delivery.                                         |

---

### 📦 **UDP Header (8 bytes total)**

|Field|Size|Description|
|---|---|---|
|Source Port|2 B|Port of the sending application|
|Destination Port|2 B|Port of the receiving application|
|Length|2 B|Length of UDP header + data|
|Checksum|2 B|Optional error-checking (IPv4)|

---

### 🎯 **Common Use Cases**

UDP is ideal when **speed matters more than reliability**.

|Application|Why UDP?|
|---|---|
|**VoIP (e.g., SIP, RTP)**|Delays > Packet Loss|
|**Online Gaming**|Real-time interaction, faster response|
|**Video Streaming (Live)**|Slight packet loss is tolerable|
|**DNS Queries**|Fast and simple; resend if needed|
|**DHCP, TFTP, SNMP**|Lightweight, minimal overhead|

---

### ⚠️ **When _Not_ to Use UDP**

Avoid UDP when you need:

- Guaranteed delivery
    
- Ordered data (e.g., file transfers)
    
- Congestion control
    

➡️ Use **TCP** instead in those cases.

### 🔁 TCP vs UDP – Protocol Comparison (OSI Layer 4)

![[Pasted image 20250420224626.png]]

| **Feature**            | **UDP (User Datagram Protocol)**                | **TCP (Transmission Control Protocol)**                     |
| ---------------------- | ----------------------------------------------- | ----------------------------------------------------------- |
| **Connection**         | Connectionless – no handshake                   | Connection-oriented – uses 3-way handshake                  |
| **Reliability**        | Unreliable – no guarantee of delivery or order  | Reliable – ensures delivery, order, and retransmission      |
| **Header Size**        | Smaller (8 bytes) – lower overhead              | Larger (20-60 bytes) – includes flags, sequence/ACK numbers |
| **Speed**              | Faster – less overhead, minimal delay           | Slower – more processing and control                        |
| **Ordering**           | No sequencing – packets may arrive out of order | Sequenced – packets are reordered before delivery           |
| **Error Checking**     | Optional checksum (IPv4), no recovery           | Checksum + error recovery via retransmission                |
| **Flow Control**       | Not supported                                   | Supported (via Window Size)                                 |
| **Congestion Control** | Not supported                                   | Supported (e.g., via TCP congestion algorithms)             |
| **Stateless**          | Yes – no session state maintained               | No – maintains state between sender and receiver            |

|**Quick Queries**|DNS, DHCP, SNMP|❌ – not necessary|
