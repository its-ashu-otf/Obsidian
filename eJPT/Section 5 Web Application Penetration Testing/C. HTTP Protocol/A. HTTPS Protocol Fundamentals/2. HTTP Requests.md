
## ⚙️ **HTTP Request Components**

---

### 🔹 1. **Request Line** (The First Line of the HTTP Request)

**Format:**

```
<HTTP Method> <Request URL> <HTTP Version>
```

**Example:**

```
GET /login HTTP/1.1
```

**Breakdown:**

- ✅ **HTTP Method** – Type of operation:
    
    - `GET`: Retrieve data
        
    - `POST`: Submit data
        
    - `PUT`: Replace/modify resource
        
    - `DELETE`: Remove a resource
        
    - `OPTIONS`, `HEAD`, `PATCH` – also used in various situations
        
- ✅ **URL/URI** – Path to resource (e.g., `/login`, `/api/data`)
    
- ✅ **HTTP Version** – Usually `HTTP/1.1`, `HTTP/2`, etc.
    

> ⚔️ **Why you care:** You can manipulate methods during testing (e.g., `PUT`, `DELETE` allowed by mistake) → **method override vulnerabilities**.

---

### 🔹 2. **Request Headers** (Metadata)

Headers provide **extra information** about the request.

**Common Headers:**

|Header|Description|
|---|---|
|`Host:`|Domain being requested (mandatory in HTTP/1.1)|
|`User-Agent:`|Info about the client (browser, tool)|
|`Accept:`|What content types the client can process (e.g., `application/json`)|
|`Authorization:`|Basic or Bearer tokens for authentication|
|`Cookie:`|Stored session data sent to the server|

> ⚔️ **Why you care:**

- Modify headers to bypass **auth** or **filters**.
    
- Use **custom User-Agent** to evade detection.
    
- Inject headers (`X-Forwarded-For`, `X-Original-URL`) to bypass **WAFs or IP filters**.
    
- Exploit **Header Injection** or **Host Header Attacks**.
    

---

### 🔹 3. **Request Body** (Optional – Used With `POST`, `PUT`, etc.)

- Contains data **sent from client to server**.
    
- Format examples:
    
    - `application/x-www-form-urlencoded` (from HTML forms)
        
    - `application/json` (used by APIs)
        
    - `multipart/form-data` (used for file uploads)
        

**Example (JSON Body):**

```http
POST /api/user HTTP/1.1
Content-Type: application/json

{
  "username": "ashu",
  "password": "root123"
}
```

> ⚔️ **Why you care:**

- Request body is **main payload attack surface** for:
    
    - SQL Injection
        
    - XSS
        
    - Command Injection
        
    - SSRF
        
    - Broken Object Level Authorization (BOLA)
        

---

### 🔍 Summary View

|Component|Purpose|Example or Use|
|---|---|---|
|Request Line|What to do & where|`GET /index HTTP/1.1`|
|Headers|Metadata about request/client|`User-Agent`, `Host`, `Cookie`|
|Body (optional)|Data sent to the server|JSON, form fields|

## ✅ **What’s Happening Step-by-Step**

### 🔹 1. **TCP Connection to [www.google.com:80](http://www.google.com/)**

- Before HTTP requests are sent, a **TCP connection** is made to port **80**.
    
- This is the **transport layer setup**, handled via a **3-way handshake**.
    

> ⚠️ **Why port 80?**

- Port **80** is the default for **HTTP** (unencrypted).
    
- Port **443** is used for **HTTPS** (encrypted via TLS).

### 🔹 3. **Understanding HTTP Request Headers**

These are **metadata** about your request:

|Header|Purpose|
|---|---|
|`GET`|The HTTP **method/verb** — in this case, we want to **fetch** the homepage (`/`).|
|`Host`|Specifies the domain (`www.google.com`). Required in HTTP/1.1.|
|`User-Agent`|Tells the server what kind of client/browser is making the request.|
|`Accept`|Tells the server what content types are acceptable (e.g., HTML, JSON).|
|`Connection`|Specifies connection behavior (`keep-alive` means reuse the TCP connection).|

![[Pasted image 20250621185308.png]]

---

### 🔹 4. **HTTP Methods (a.k.a. HTTP Verbs)**

These methods define **what action** the client wants the server to take on a resource.

|Method|Action|Typical Use Case|
|---|---|---|
|`GET`|Retrieve resource (read only)|View pages, fetch data|
|`POST`|Submit data to server|Logins, forms|
|`PUT`|Replace a resource|API updates|
|`DELETE`|Remove a resource|API deletions|
|`OPTIONS`|Ask server what methods are allowed|CORS preflights|
|`HEAD`|Like GET but only headers (no body)|Lightweight checks|
|`PATCH`|Partial update of a resource|Updating one field|

> ⚔️ **Pentester’s Tip:**

- Try **verb tampering** — e.g., use `POST` instead of `GET`, or try `OPTIONS` to enumerate allowed methods.
    
- Some misconfigured servers will allow dangerous methods like `PUT` or `DELETE`.
    

---

## 🔍 In Summary:

- A TCP connection is first made to port 80.
    
- An HTTP request is then sent using the **GET** method (most common).
    
- Headers provide **info about the request/client**.
    
- HTTP methods define **what you want the server to do**.


# HTTP Request Method Explained

### 🔹 `GET`

- **Function:** Retrieve data (e.g., HTML, JSON).
    
- **Side Effects:** ❌ No — purely read-only.
    
- **Idempotent:** ✅ Yes — same request → same result.
    
- **Body Allowed:** ❌ No (technically possible but not used).
    
- **Example:**
    
    ```
    GET /profile?id=123 HTTP/1.1
    ```
    
- ⚔️ **As a Pentester:**
    
    - Test query parameter injections (`id=123' OR 1=1`)
        
    - Look for sensitive data leakage in URL or response.
        

---

### 🔹 `POST`

- **Function:** Submit data for processing (e.g., forms, logins).
    
- **Side Effects:** ✅ Yes — can modify server state.
    
- **Idempotent:** ❌ No — multiple submissions = multiple changes.
    
- **Body Allowed:** ✅ Yes (JSON, form data, etc.)
    
- **Example:**
    
    ```
    POST /login HTTP/1.1
    Content-Type: application/x-www-form-urlencoded
    
    username=admin&password=1234
    ```
    
- ⚔️ **As a Pentester:**
    
    - Look for **auth bypass**, **SQLi**, **CSRF**, **XSS**, etc.
        
    - Replay POST requests to test for **duplicate actions** (e.g., money transfers).
        

---

### 🔹 `PUT`

- **Function:** Replace or create a resource.
    
- **Side Effects:** ✅ Yes — overwrites data.
    
- **Idempotent:** ✅ Yes — same PUT request = same state.
    
- **Body Allowed:** ✅ Yes
    
- **Example:**
    
    ```
    PUT /user/ashu HTTP/1.1
    Content-Type: application/json
    
    {
      "name": "Ashu",
      "role": "admin"
    }
    ```
    
- ⚔️ **As a Pentester:**
    
    - Test if PUT is enabled ⇒ **upload shell, overwrite resources**
        
    - Look for improper access control (e.g., unauthorized resource overwrite)
        

---

### 🔹 `DELETE`

- **Function:** Delete the resource.
    
- **Side Effects:** ✅ Yes — removes data.
    
- **Idempotent:** ✅ Yes
    
- **Body Allowed:** Technically yes, but often ignored.
    
- **Example:**
    
    ```
    DELETE /user/ashu HTTP/1.1
    ```
    
- ⚔️ **As a Pentester:**
    
    - Test for improper method restrictions
        
    - If DELETE is enabled, try unauthorized data deletion
        

---

### 🔹 `PATCH`

- **Function:** Partially update a resource.
    
- **Side Effects:** ✅ Yes
    
- **Idempotent:** ✅/❌ (depends on implementation)
    
- **Body Allowed:** ✅ Yes (usually JSON)
    
- **Example:**
    
    ```
    PATCH /user/ashu HTTP/1.1
    Content-Type: application/json
    
    {
      "role": "admin"
    }
    ```
    
- ⚔️ **As a Pentester:**
    
    - Test for **BOLA (Broken Object Level Authorization)**
        
    - Check if partial updates expose other users' fields
        

---

### 🔹 `HEAD`

- **Function:** Like GET but **only headers**, no body.
    
- **Purpose:** Check resource metadata (existence, size, last-modified).
    
- **Idempotent:** ✅ Yes
    
- **Example:**
    
    ```
    HEAD /index.html HTTP/1.1
    ```
    
- ⚔️ **As a Pentester:**
    
    - Use to check if a file exists without downloading it.
        
    - Useful in **stealth scanning** or **file discovery**.
        

---

### 🔹 `OPTIONS`

- **Function:** Ask the server what methods are allowed.
    
- **Used For:** CORS preflight, API discovery
    
- **Idempotent:** ✅ Yes
    
- **Example:**
    
    ```
    OPTIONS /api/data HTTP/1.1
    ```
    
- ⚔️ **As a Pentester:**
    
    - Use to **enumerate allowed HTTP methods**.
        
    - If `PUT`, `DELETE` are allowed — try them!
        
    - Can reveal **CORS misconfigurations**.
        

---

### 🧠 TL;DR Table

|Method|Safe|Idempotent|Has Body|Use For|
|---|---|---|---|---|
|GET|✅|✅|❌|Reading data|
|POST|❌|❌|✅|Sending data|
|PUT|❌|✅|✅|Replace or create|
|DELETE|❌|✅|❌|Delete data|
|PATCH|❌|❌|✅|Partial update|
|HEAD|✅|✅|❌|Check if resource exists|
|OPTIONS|✅|✅|❌|Get allowed methods, CORS info|

# HTTP Request URL/Path

## 🌐 **Understanding the URI in HTTP Requests**

---

### 🔹 What is a URI?

- **URI (Uniform Resource Identifier)** is the **path** the client uses to tell the server **which resource to fetch**.
    
- It comes **immediately after the method** in the HTTP request line.
    

**Example:**

```http
GET /downloads/index.php HTTP/1.1
```

- Here:
    
    - `GET` is the method
        
    - `/downloads/index.php` is the **URI**
        
    - `HTTP/1.1` is the protocol version

![[Pasted image 20250621192116.png]]

---

### 🔸 Key Notes:

#### ✅ Root Path = `/`

- When you visit a homepage like `http://example.com`, you're really requesting:
    
	    GET / HTTP/1.1
    
- The `/` refers to the **root directory** on the web server — like `/var/www/html/` on Linux servers using Apache or Nginx.
    

#### ✅ Other URIs:

- Any other path, like `/login`, `/products/item123`, etc., points to subdirectories or files.
    
- These paths **map to files or routes** handled by the web server or backend application.
    

---

### 🧠 Why It Starts With `/`

- The leading `/` represents the **root directory** — similar to Linux.
    
- You're always starting from the top level of the server’s web root.

```bash
/downloads/index.php → refers to: [web root]/downloads/index.php> 
```

---

### ⚔️ **Pentester’s Angle**

- **URIs are attack surfaces.** You test them for:
    
    - Path traversal (`../../etc/passwd`)
        
    - Hidden endpoints (`/admin`, `/backup.zip`)
        
    - Insecure direct object references (`/user/1002`)
        
    - Parameter tampering (`/invoice?id=999`)
        
- You can brute-force directories and files using tools like:
    
    - `gobuster`
        
    - `dirb`, `dirbuster`
        
    - Burp Suite’s **Intruder** or **Content Discovery**
        

---

### 📌 Real Example:

**Request:**

```
GET /login.php HTTP/1.1
Host: vulnerable.site
```

- URI: `/login.php` → server fetches the login script
    
- You might test:
    
    - `/login.php?user=admin'--`
        
    - `/login.php.bak`
        
    - `/login/` (in case it's a directory)

# HTTP Request Host Header

- This is the beginning of HTTP Request Headers. HTTP Headers have the following structure: `Header-name:Header-Value`. 
- The Host header allows a web server to host multiple websites at a single IP address. Our browser is specifying in the Host header which website you are interested in.

![[Pasted image 20250621195634.png]]

- After each request header, you will find its corresponding value. In this case we want to access the Host www.google.com. 
- **Note:** Host value + Path combine to create the full URL you are requesting: the home page of www.google.com/

# HTTP Request User-Agent Header

-  The User-Agent is used to specify and send your browser, browser version, operating system and language to the remote web server.  
- All web browsers have their own user-agent identification string. This is how most web sites recognize the type of browser in use.

![[Pasted image 20250621200045.png]]

# HTTP Request Accept Header 
-  The Accept header is used by your browser to specify which document/file types are expected to be returned from the web server as a result of this request.

![[Pasted image 20250621200123.png]]

# HTTP Request Accept-Encoding Header 
- The Accept-Encoding header is similar to Accept, and is used to restrict the content encoding that is acceptable in the response. 
- Content encoding is primarily used to allow a document to be compressed or transformed without losing the original format and without the loss of information.

![[Pasted image 20250621200210.png]]

# HTTP Request Connection Header

- When using HTTP 1.1, you can maintain/re-use the connection to the remote web server for an unspecified amount of time using the value "keep-alive". 
- This indicates that all requests to the web server will continue to be sent through this connection without initiating a new connection every time (as in HTTP 1.0).
