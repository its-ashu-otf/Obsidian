# HTTP (Hypertext Transfer Protocol): Core Overview

- **Layer:** Application Layer (OSI Layer 7)
    
- **Nature:** Stateless protocol
    
    > Each HTTP request is independent — server doesn't retain session info between requests unless explicitly handled (e.g., via cookies, sessions, JWT).
    
- **Runs Over:** TCP (typically on port **80**)
    

---

### 🔹 **Purpose**

- Designed for **communication between clients (browsers)** and **servers (web servers)**.
    
- Transfers **HTML**, **CSS**, **JavaScript**, images, APIs, and other web resources.
    

---

### 🔹 **Architecture**

- **Client-Server Model**
    
    - **Client:** Web browser or tools like `curl`, `Postman`, `Burp Suite`, etc.
        
    - **Server:** Hosts and serves the content (Apache, Nginx, IIS, etc.).
        
- Resources are addressed using:
    
    - **URL (Uniform Resource Locator)** or
        
    - **URI (Uniform Resource Identifier)**
        

---

### 🔹 **HTTP Versions**

#### ⚫ HTTP/1.0:

- One connection per request.
    
- No persistent connections — each request opens a new TCP connection (slow and resource-heavy).
    

#### ⚫ HTTP/1.1 (most common):

- **Persistent Connections (Keep-Alive):** Reuses the same TCP connection for multiple requests.
    
- **Pipelining:** Allows multiple requests to be sent before receiving responses.
    
- **Chunked Transfer Encoding:** Handles dynamic content better.
    
- **Additional headers like Host:** Makes virtual hosting possible.
    

---

### 🔹 ⚔ Pentesting Tip:

- **Why you care as a pentester?**
    
    - Understanding how HTTP behaves helps in:
        
        - **Manual testing via Burp Suite or cURL**
            
        - **Exploiting misconfigured headers or methods (e.g., PUT, TRACE)**
            
        - **Identifying injection points in GET/POST parameters**
            
        - **Testing authentication/session management vulnerabilities**

This diagram is a **basic representation of how HTTP/HTTPS communication works** between a **client (browser)** and a **server (web server)**. Let's break it down simply and precisely:

---

### 🔁 **Components Involved**

- **Browser (Client):** Initiates communication; sends requests to get or send data.
    
- **Web Server:** Receives requests and responds with the requested content (like HTML, images, APIs).
    

---

### 🔹 **Communication Flow (Labelled in Diagram)**

#### 1. **HTTP Request** 🔼

- Initiated by the browser.
    
- Examples:
    
    - `GET /index.html HTTP/1.1`
        
    - `POST /login HTTP/1.1`
        
- Sent over either:
    
    - **HTTP (insecure)** — uses **port 80**
        
    - **HTTPS (secure)** — uses **port 443**, encrypted via SSL/TLS
        

#### 2. **HTTP/S (the transport medium)**

- This is the **protocol layer** over TCP.
    
- **HTTP:** Plaintext, visible to MITM attacks.
    
- **HTTPS:** Encrypted using SSL/TLS, provides:
    
    - Confidentiality
        
    - Integrity
        
    - Authentication
        

#### 3. **HTTP Response** 🔽

- Sent back from server to browser.
    
- Contains:
    
    - **Status Code** (e.g., 200 OK, 404 Not Found)
        
    - **Headers**
        
    - **Body** (actual content like HTML, JSON, etc.)

---

## 🕰️ History of HTTP Protocol

### 🔹 **1991 – HTTP/0.9** (The Barebones Start)

- **Created by Tim Berners-Lee**
    
- **Purpose:** Serve simple HTML pages
    
- **Method Supported:** Only `GET`
    
- **No Headers**, no status codes, no metadata — just raw HTML as response.
    
- **No support for media, CSS, or any interactive content.**
    

> ⚔️ Pentester’s Note: Nothing to exploit here; it’s ancient and unused today.

---

### 🔹 **1996 – HTTP/1.0** (Structured and Formal)

- **First official HTTP version (RFC 1945)**
    
- Introduced:
    
    - **Headers** (e.g., Content-Type, Content-Length)
        
    - **Status codes** (e.g., 200 OK, 404 Not Found)
        
    - Support for different request methods: `GET`, `POST`, `HEAD`
        
- Still **stateless** and **non-persistent**: Each request opens a new TCP connection.
    

> ⚔️ Attack Vectors:

- Still simple, but vulnerabilities started emerging (e.g., information leakage, basic auth flaws).

---

### 🔹 **1999 – HTTP/1.1** (Modern Standard)

- Defined in **RFC 2616**, later updated by RFC 7230–7235.
    
- Became **default HTTP version** for most of the web.
    
- Key improvements:
    
    - **Persistent connections** (keep-alive)
        
    - **Chunked transfer encoding**
        
    - **Pipelining** support (multiple requests before first response arrives)
        
    - **Host header** (allowed virtual hosting — multiple domains on one IP)
        
    - New methods: `OPTIONS`, `PUT`, `DELETE`, `TRACE`
        

> ⚔️ Common Pentesting Targets:

- **Header injection**, **verb tampering**, **request smuggling**, **directory traversal**, etc.
    
- Proxy abuse using `CONNECT`, `TRACE` methods.
    

---

### 🔹 **2015 – HTTP/2** (Performance-Oriented)

- **RFC 7540**, developed by the IETF based on Google’s SPDY protocol.
    
- **Backwards compatible** with HTTP/1.1 semantics (same methods, status codes).
    
- Major technical shifts:
    
    - **Binary protocol** (not plain text)
        
    - **Multiplexing** (multiple concurrent streams over one TCP connection)
        
    - **Header compression** (HPACK)
        
    - **Stream prioritization**
        

> ⚔️ Considerations:

- Harder to manually intercept without tools that understand HTTP/2 (e.g., Burp with support enabled)
    
- Still vulnerable to logical flaws and TLS misconfig.
    

---

### 🔹 **2022 – HTTP/3** (Speed + Security)

- Built on top of **QUIC** (UDP-based transport layer protocol).
    
- Benefits:
    
    - **Faster connection establishment** (0-RTT)
        
    - **Better handling of packet loss**
        
    - **Always encrypted** (no plain HTTP/3 — it runs on QUIC+TLS 1.3)
        

> ⚔️ Penetration Testing Notes:

- You’ll need tools that support HTTP/3/QUIC (e.g., Wireshark, curl with HTTP/3 support).
    
- **DNS over HTTPS (DoH)** and **encrypted transport** limit visibility in MITM scenarios.
    

---

## 📌 Summary Table

|Version|Year|Key Features|Status|
|---|---|---|---|
|HTTP/0.9|1991|GET only, no headers|Obsolete|
|HTTP/1.0|1996|Headers, status codes, multiple methods|Obsolete|
|HTTP/1.1|1999|Persistent connections, Host header, pipelining|Widely used|
|HTTP/2|2015|Binary, multiplexing, header compression|Increasing usage|
|HTTP/3|2022|QUIC, UDP-based, 0-RTT, TLS 1.3|Gaining adoption|

---

### 🔒 **Key Point (Security)**

- If the connection is **HTTP**, an attacker can:
    
    - Sniff the traffic
        
    - Modify responses
        
    - Inject scripts (MiTM, Downgrade attacks)
        
- If the connection is **HTTPS**, such threats are mitigated by encryption.

---

### ✅ **HTTP Message Structure**

#### 🔹 1. **HEADERS\r\n**

- This is the **header section** of the HTTP message.
    
- It includes key-value pairs like:

```http
    Host: example.com
    User-Agent: Mozilla/5.0
    Accept: text/html
```

- Each header line ends with `\r\n`.
    
- After all headers, there’s one blank line to separate headers from the body — this is **just `\r\n` alone**.
    

#### 🔹 2. **\r\n (Blank Line)**

- Marks the **end of headers**.
    
- It is critical in HTTP — without this line, the server won’t know when the headers end and the body begins.
    

#### 🔹 3. **MESSAGE BODY**

- This is the **optional content** part of the request or response.
    
    - For **GET** requests, usually there’s no body.
        
    - For **POST**, **PUT**, etc., it might contain form data, JSON, etc.
        
- Also ends with `\r\n` optionally (especially in plain text).
    

---

### ⚙️ **What is `\r\n`?**

On the right side of the image:

- `\r` (Carriage Return): Moves the cursor back to the start of the line.
    
- `\n` (Line Feed): Moves the cursor to the **next** line.
    
- Combined `\r\n`: Standard for marking line breaks in network protocols like HTTP (equivalent to pressing "Enter").
    

> 📌 **Used in:** All HTTP versions, including 1.0, 1.1, and sometimes in raw socket manipulation tools.

---

### 🔁 **Client-Server Exchange**

Here's how the full flow works:

1. **Client sends an HTTP Request**, like:
    
    ```
    GET /index.html HTTP/1.1\r\n
    Host: example.com\r\n
    User-Agent: Mozilla\r\n
    \r\n
    ```
    
2. **Server responds with an HTTP Response**, like:
    
    ```
    HTTP/1.1 200 OK\r\n
    Content-Type: text/html\r\n
    Content-Length: 1024\r\n
    \r\n
    <html> ... </html>
    ```

    - Exploiting **header injection** vulnerabilities
