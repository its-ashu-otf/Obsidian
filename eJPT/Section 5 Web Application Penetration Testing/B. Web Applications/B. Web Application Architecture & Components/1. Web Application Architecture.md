## 🔧 What is Web Application Architecture?

Web application architecture is the **blueprint** for how a web app’s **components** (frontend, backend, databases, etc.) **communicate and interact**. It outlines:

- The **flow of data**
    
- The **responsibilities** of each layer (client/server)
    
- How **requests/responses** are processed
    
- And most importantly, how to **design** for performance, security, and scalability
    

It’s essential to understand this architecture before conducting any security assessment — it helps you **predict where vulnerabilities may exist**, how to access or manipulate data, and identify misconfigurations.

---

## 🧱 The Core Model: **Client-Server Architecture**

![[Pasted image 20250620001652.png]]

Most modern web applications follow the **Client-Server model**. It breaks the app into two major halves:

### 1. **Client (Front-End)**

- Runs in the **user's web browser**
    
- Handles **UI/UX**, input collection, and sending requests
    
- Technologies: **HTML, CSS, JavaScript**
    
- Interacts with the server by sending **HTTP requests**
    

### 2. **Server (Back-End)**

- Hosted on a **remote machine** (or cloud service)
    
- Handles **business logic**, data processing, authentication
    
- Talks to **databases** and returns results
    
- Technologies: **PHP, Python, Java, Node.js, Ruby**, etc.
    

```text
Client <--- HTTP/HTTPS ---> Server <--- SQL/NoSQL ---> Database
```

## 🖥️ Client-Side Processing (Browser)

### 🔸 What It Does

Client-side processing means the browser (on the user’s machine) performs tasks **locally**, using JavaScript.

### 🔸 Key Features

- **Fast**: No need to wait for server replies
    
- **Used for**: UI updates, form validation, animations, user input handling
    
- **Risks**: It’s **insecure for sensitive tasks**—code is visible, modifiable, and hackable by users
    

### 🔸 Technologies Involved

- **HTML** – Structures the content
    
- **CSS** – Styles the interface
    
- **JavaScript** – Adds interactivity and logic
    

### 🔸 Example

- Validating a login form’s input before sending it to the server
    
- Updating content dynamically with `AJAX` or `Fetch API`
    

---

## 🗃️ Server-Side Processing (Backend)

### 🔹 What It Does

Happens on the **server**, where all **critical operations** take place—data processing, user authentication, permission checks, etc.

### 🔹 Key Features

- **Secure**: Code and logic are hidden from users
    
- **Handles**: Database interaction, logic, heavy computation
    
- **Languages**: PHP, Python, Java, Node.js, Ruby, etc.
    

### 🔹 Example

- Authenticating credentials against a user database
    
- Sending a password reset email

## 🔁 Communication and Data Flow

Web applications use **HTTP/HTTPS** (stateless protocols) to facilitate client-server communication.

### 🧭 Step-by-Step Flow:

1. **User Interacts**
    
    - Example: Clicks "Login" on a form
        
2. **Browser Sends Request (HTTP Request)**
    
    - Contains method: `GET`, `POST`, `PUT`, `DELETE`
        
    - Includes headers, cookies, and sometimes body (e.g., login credentials)
        
3. **Web Server Receives the Request**
    
    - If it’s a static resource (e.g., CSS/JS), it returns it immediately
        
    - Otherwise, it forwards to the **application server**
        
4. **Application Server Processes the Request**
    
    - Validates input, checks user credentials
        
    - Talks to **database** to fetch/store data
        
    - Executes **business logic**
        
5. **Database Interaction**
    
    - Sends `SQL` or `NoSQL` queries to fetch or write data
        
    - Response sent back to the application server
        
6. **Server Constructs an HTTP Response**
    
    - Dynamic HTML or JSON
        
    - Includes session tokens, cookies, headers, etc.
        
7. **Client Receives Response**
    
    - Browser renders HTML, or JS processes JSON to update UI
        

---

### 💬 Example: User Login

1. User fills in username/password → clicks "Submit"
    
2. Browser sends `POST /login` to the server
    
3. Server hashes the password and compares it to database
    
4. If match: create session, set `Set-Cookie: sessionID=xyz`
    
5. Send `200 OK` with user dashboard
    
6. Browser stores the cookie and shows the dashboard

## ⚠️ Security Perspective

Understanding the architecture allows you to:

- **Identify attack surfaces** (client, server, DB)
    
- Know where to test for:
    
    - **Client-Side**: XSS, DOM-based attacks
        
    - **Server-Side**: SQLi, RCE, IDOR, auth bypass
        
    - **Communication**: MITM, session hijacking, CSRF
        
- Recognize **entry points** (form inputs, APIs, hidden parameters)

## 🔧 Web Application Components Explained

### 1. **User Interface (UI)**

- **What it is:**  
    The visual layer that users see and interact with — rendered in the web browser.
    
- **Includes:**  
    Web pages, input forms, buttons, menus, dashboards, icons.
    
- **Purpose:**  
    Captures user input, presents data, and triggers client-side or server-side events.
    
- **Security Implication:**  
    UI elements can be manipulated by attackers for client-side attacks like **XSS**, **clickjacking**, or input tampering.
    

---

### 2. **Client-Side Technologies**

- **Examples:**
    
    - **HTML:** Defines page structure
        
    - **CSS:** Styles and layouts
        
    - **JavaScript:** Adds interactivity and dynamic behavior
        
- **Function:**  
    These run in the browser and are responsible for rendering the UI, handling real-time interactions (like drag-and-drop or animations), and making asynchronous requests (via **AJAX** or **fetch**).
    
- **Security Implication:**  
    Vulnerable to **DOM-based XSS**, local storage abuse, insecure JavaScript libraries, and client-side validation bypasses.
    

---

### 3. **Server-Side Technologies**

- **Languages & Frameworks:**  
    PHP, Python (Django/Flask), Java (Spring), Ruby (Rails), Node.js (Express), etc.
    
- **Function:**
    
    - Execute application logic
        
    - Authenticate users
        
    - Handle business rules
        
    - Interact with databases
        
    - Generate dynamic responses (HTML, JSON, XML, etc.)
        
- **Security Implication:**  
    Entry point for **SQL Injection**, **RCE**, **LFI/RFI**, **authentication flaws**, **IDOR**, **authorization bypass**, etc.
    

---

### 4. **Databases**

- **Types:**
    
    - **Relational:** MySQL, PostgreSQL, MSSQL
        
    - **NoSQL:** MongoDB, CouchDB, Redis
        
- **Function:**  
    Stores all persistent application data:
    
    - User credentials, session tokens
        
    - Posts, messages, settings
        
    - Configuration data
        
- **Security Implication:**
    
    - Improper input handling can lead to **SQLi/NoSQLi**
        
    - Weak permissions can lead to **privilege escalation**
        
    - Misconfigurations (open ports, no auth) may allow **unauthorized access**
        

---

### 5. **Application Logic**

- **Function:**
    
    - Governs how the application behaves
        
    - Defines rules for registration, login, payments, workflows, etc.
        
    - Includes:
        
        - **Authentication/Authorization**
            
        - **Input validation**
            
        - **Session management**
            
        - **Rate limiting**
            
- **Security Implication:**
    
    - Logic flaws can be exploited for **business logic bypass**
        
    - Weak or missing input validation may allow **injection** attacks
        
    - Poor session handling leads to **session fixation/hijacking**
        

---

### 6. **Web Servers**

- **Examples:** Apache, Nginx, IIS
    
- **Function:**
    
    - Serve static files (HTML, JS, CSS, images)
        
    - Route incoming HTTP/HTTPS requests to the correct application handlers (e.g., reverse proxy to app server)
        
- **Additional Features:**
    
    - SSL termination
        
    - URL rewriting
        
    - Access control and logging
        
- **Security Implication:**
    
    - **Directory traversal**
        
    - **File inclusion bugs**
        
    - **Misconfigured access controls**
        
    - Leaking of **internal paths or source code** (if error handling is poor)
        

---

### 7. **Application Servers**

- **Examples:**  
    Tomcat (Java), uWSGI (Python), Passenger (Ruby), Node.js (native), Gunicorn (Python)
    
- **Function:**
    
    - Executes the core application backend logic
        
    - Handles user sessions, API requests
        
    - Communicates with databases and external services
        
- **Security Implication:**
    
    - Improper sandboxing can lead to **RCE**
        
    - Weak isolation or exposed internal APIs can be abused for **lateral movement**
        
    - May be vulnerable to **deserialization**, **file upload flaws**, or **misconfigured CORS**

## 🧠 Why This Matters for a Security Assessment

Understanding the role of each component helps in:

- **Identifying attack vectors** (e.g., target JS files on the client, test backend APIs)
    
- **Prioritizing tests** based on component sensitivity (e.g., DB → high-value target)
    
- **Mapping attack surface** for enumeration and footprinting
    
- **Recognizing patterns** (e.g., MVC vs Microservices affects where logic lives)

## 🕵️ Example Attack Flow Using Component Knowledge

1. **Start at the UI:**  
    Discover input points and try **client-side validation bypass**.
    
2. **Use dev tools (F12):**  
    Inspect JS files, discover hidden API endpoints.
    
3. **Send requests directly to the server:**  
    Use **Burp Suite** to manipulate requests (POST to `/api/user/update`)
    
4. **Fuzz the server-side logic:**  
    Attempt **SQLi**, **IDOR**, **auth bypass**
    
5. **Attack the database:**  
    Use successful injection to dump or escalate
    
6. **Look for server misconfigs or outdated components** for RCE or DoS
