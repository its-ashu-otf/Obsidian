# 🔐 Windows Access Tokens – Explained

### 🔸 What Are Access Tokens?

A **Windows Access Token** is a **security object** used to represent the **security context** (identity and permissions) of a process or thread. It's a key component of the Windows **authentication and authorization** system.

> Think of it like a _digital passport_ or _session cookie_ — once you're authenticated, Windows attaches this token to every process you launch to avoid re-authentication.

---

### 🧬 How They're Created

1. **User logs in** → `winlogon.exe` triggers authentication.
    
2. Upon successful login, **LSASS** (Local Security Authority Subsystem Service) generates an **access token**.
    
3. This token is attached to `userinit.exe`.
    
4. All **child processes** inherit this token — meaning all user actions/processes carry the same privileges unless explicitly changed.
    

---

### 📦 What's Inside an Access Token?

A typical token contains:

- **User SID**
    
- **Group SIDs**
    
- **Privileges** (e.g., `SeDebugPrivilege`)
    
- **Integrity level** (Low, Medium, High, System)
    
- **Token type** (Primary or Impersonation)
    
- **Session ID**
    
- **Restricted SIDs** (if applicable)
    

---

### 🎭 Token Types (Based on Security Level)

|Token Type|Created by|Usage Scope|Risk Level|
|---|---|---|---|
|**Impersonation**|Non-interactive logins (e.g., services)|Can impersonate _only_ locally|Low|
|**Delegation**|Interactive logins (GUI, RDP)|Can be used to impersonate on **remote systems**|High|

> 🧠 **Delegate-level tokens are gold for attackers** — they can be reused across systems, enabling lateral movement.

---

### 🔐 Token Usage and Inheritance

- **Primary Tokens**: Associated with a process. Only created by the OS or with `CreateProcessAsUser()`.
    
- **Impersonation Tokens**: Used by threads to temporarily "borrow" another user’s security context.
    

Any child process will **inherit the token** of its parent unless explicitly modified.

---

## ⚔️ Why Tokens Matter in Pentesting

### 🔓 Token-Based Attacks (Post-Exploitation)

Attackers can:

- **Steal tokens** via LSASS memory dump (`mimikatz` → `sekurlsa::tokens`)
    
- **Duplicate tokens** (Token Impersonation/Delegation)
    
- **Create processes** under stolen tokens (e.g., `CreateProcessWithTokenW`)
    
- **Pass-the-Token (PTT)** attacks for lateral movement
    

### 🧰 Tools Used:

- **Mimikatz**: `token::list`, `token::elevate`, `sekurlsa::tokens`
    
- **Rubeus**: For Kerberos ticket abuse (related but distinct)
    
- **Incognito** (Metasploit): Classic tool for token manipulation
    

---

## 🛡️ Defensive Notes

- **LSASS protection**: Enable Credential Guard or run LSASS as a protected process.
    
- **Event Logging**: Monitor for use of token manipulation API calls (`CreateProcessWithTokenW`, etc.)
    
- **Group Policy**: Limit use of delegate tokens (e.g., restrict RDP access).
    
- **Use AppLocker/WDAC**: Restrict execution of token-grabbing tools.
    

---

## 🔁 Summary (TL;DR)

|Concept|Explanation|
|---|---|
|**What**|A temporary object that defines a user's security context (identity + privileges)|
|**Created By**|LSASS, after login (via `winlogon.exe`)|
|**Used For**|Authorizing access to files, services, registry, etc.|
|**Types**|Primary, Impersonation (Impersonate, Delegate)|
|**Attack Vectors**|Token theft, impersonation, lateral movement via delegation|
|**Defense**|Monitor LSASS, secure delegation, enable process protection|

# 🛡️ Windows Privileges – Core to Token Impersonation

In Windows, **privileges** define what actions an account or process can perform at the system level — beyond simple ACL-based file access.

During **post-exploitation**, if you're planning to:

- **Steal or impersonate tokens**,
    
- **Create new processes under another user’s context**, or
    
- **Forge tokens to escalate privileges**,
    

then you’ll need **specific system privileges**.

---

### 🎯 Key Privileges for Token-Based Privilege Escalation

|Privilege Name|Description|
|---|---|
|**SeAssignPrimaryToken**|Allows a user to **assign a primary token** to a process. Essential for `CreateProcessAsUser()`|
|**SeCreateTokenPrivilege**|Allows creation of **custom tokens** from scratch (rarely granted, very powerful)|
|**SeImpersonatePrivilege**|Allows a process to **impersonate another user** after authentication — especially useful with named pipes or service abuse (e.g., Potato attacks)|

> 🧠 These privileges are **normally restricted to SYSTEM or high-integrity service accounts**, but some misconfigurations allow attackers to gain access.

---

## 🎭 Practical Exploitation: Impersonation & Delegation

After gaining a foothold:

- If you're SYSTEM, you can impersonate _any user_.
    
- If you have `SeImpersonatePrivilege`, you can abuse it via:
    
    - **Potato exploits** (e.g., Juicy Potato, Rogue Potato, PrintSpoofer)
        
    - **Named pipe impersonation**
        

---

### 🧰 The Incognito Module – Token Abuse Simplified

**Incognito** is a **Meterpreter** module (also available in standalone form) designed to:

- **List** available tokens on the system (`list_tokens -u` for user, `-g` for groups)
    
- **Impersonate** a token (`impersonate_token <domain\\user>`)
    
- **Add a user to a local group** (if the token allows)
    

---

#### 🔥 Sample Workflow with Incognito (Post Shell):

```bash
meterpreter > use incognito
meterpreter > list_tokens -u
meterpreter > impersonate_token "DOMAIN\\Administrator"
```

If successful, the current Meterpreter session now runs with **Administrator privileges** under that token.

> ⚠️ Tokens must be **available in memory** — typically from running sessions, services, or cached logins.

---

## 🛑 Real-World Application in Attacks

- **Lateral Movement**: Using stolen delegate tokens across systems.
    
- **Local Privilege Escalation**: Abuse impersonation privileges to become SYSTEM.
    
- **Persistence**: Leverage impersonated tokens to install services, backdoors, or create users.
    

---

## 🧯 Defense Tips (Blue Team):

|Mitigation Area|Action|
|---|---|
|**Privileged Accounts**|Limit `SeImpersonate`, `SeAssignPrimaryToken`, and `SeCreateToken` only to trusted services|
|**Monitoring**|Log and alert on use of `CreateProcessAsUser()`, `ImpersonateLoggedOnUser()`, `DuplicateTokenEx()`|
|**Token Hygiene**|Avoid long-lived interactive logins, especially over RDP|
|**Credential Guard**|Prevents access to credentials and tokens in LSASS|
|**AppLocker/WDAC**|Blocks unsigned tools like Incognito or Mimikatz|

---

## 🧠 Summary Table

|Component|Purpose/Use Case|
|---|---|
|**SeAssignPrimaryToken**|Run a process with a specified token|
|**SeCreateToken**|Create a custom token (rare)|
|**SeImpersonatePrivilege**|Impersonate another user's security context|
|**Incognito Tool**|Abuse and list tokens in memory after exploit|
|**Meterpreter Integration**|Built-in incognito module for quick usage|
